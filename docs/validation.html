Validation

Rules on validateable components, validate-on-blur, lkValidation for whole forms, custom rules and server errors

Validateable components

These components accept a rules option and expose the same validation API: lkTextbox, lkDropdown (single & multiple), lkCheckbox, lkRadio, lkSwitch, lkPhone and lkTextPop.

MemberWhat it does
rules option / propertyArray of rules checked in order; the first failing rule's message is shown.
validate: true optionRun the rules automatically when focus leaves the component (alias validateOnBlur).
.validate()Run the validation manually. Shows/clears the message and returns true when valid.
.validateAsync()Same, but waits for async rules (e.g. “is this username free?”). Resolves true / false.
.setValidation(message)Set a validation message manually (e.g. from the server).
.clearValidation()Clear the validation manually and return the field to its initial, untouched state.
.error / .hasError / .validatingCurrent message (null when valid) / whether one is shown / whether an async rule is running.
Look.lkValidation(a, b, …)Groups components: validate() / validateAsync() run every member and return { hasError, errors }; setErrors(map) shows server messages; submit(handler) does validate → save → map 422 errors.

Live example

Username, Password, Role and Mobile use validate: true (checked when you leave them); the others are checked by Submit through lkValidation. After a field has been validated it re-checks itself while you edit it. Username also has an async rule: root, jane and support are “taken” (watch the spinner by the label). Submit uses form.submit() with a fake server that answers 422 for the username admin and emails at example.com.

JavaScript (excerpt of the example above)

const username = Look.lkTextbox('#username', {
  label: 'Username',
  validate: true,                                    // check on blur
  rules: [
    'required',
    { minLength: 3, message: 'At least 3 characters' },
    (v) => /^[a-z0-9_]+$/.test(v) || 'Lowercase letters, digits and _ only',
  ],
});
const email   = Look.lkTextbox('#email', { label: 'Email', rules: ['required', 'email'] });
const confirm = Look.lkTextbox('#confirm', {
  label: 'Confirm password',
  rules: ['required', (v) => v === password.value || 'Passwords do not match'],   // cross-field
});
const skills  = Look.lkDropdown('#skills', { multiple: true, items, rules: [{ minLength: 2, message: 'Pick at least 2' }] });
const phone   = Look.lkPhone('#phone', { label: 'Mobile', required: true, validate: true });
const manager = Look.lkTextPop('#manager', { label: 'Manager', dataSource: people, rules: ['required'] });
const terms   = Look.lkCheckbox('#terms', { label: 'I accept the terms', rules: [{ required: true, message: 'Please accept the terms' }] });

const form = Look.lkValidation(username, email, confirm, skills, phone, manager, terms, { loading: '#form' });

formEl.addEventListener('submit', async (e) => {
  e.preventDefault();
  const res = await form.submit(async () => {           // validateAsync() first; stops if invalid
    const r = await fetch('/api/users', { method: 'POST', body: new FormData(formEl) });
    if (!r.ok) throw await r.json();                      // 422 { message, errors: { username: [...] } }
    return r.json();
  });
  if (res.ok) Look.lkToast({ type: 'positive', title: 'Saved' });
  else if (res.reason === 'error') Look.lkToast({ type: 'negative', title: 'Not saved', message: res.message });
});

How validation runs

  1. Untouched. A new field shows no message, even if it is empty.
  2. Validated. A field is validated by .validate(), by lkValidation().validate(), or—with validate: true—when focus leaves it. For pickers (dropdown, phone country list, text pop) leaving means the panel is closed and focus is outside the component.
  3. Touched. From then on, each change the user makes (typing, picking, ticking) re-runs the rules, so a message disappears as soon as the value is fixed. Setting .value from code does not re-run them—call .validate() or .clearValidation() yourself.
  4. Reset. .clearValidation() removes the message and returns the field to untouched.

Async rules. A function rule may return a Promise that resolves to true or a message:

  • Results are cached per value, so checking the same value twice does not call the server again.
  • While the user edits a validated field, sync rules run at once and async rules wait for a pause in typing (validateDebounce, 400 ms).
  • A result that arrives after the value changed, or after a newer validation, is ignored — a slow response never overwrites a newer one.
  • While one runs, .validating is true, the field gets .lk-field--validating (a spinner by the label) and aria-busy.
  • .validate() does not wait: it uses cached results and lets uncached async rules finish in the background. Use .validateAsync(), lkValidation().validateAsync() or submit() before saving.

The required option (or a required attribute) counts as the first rule, with the message “Label is required” (“This option is required” for checkbox / switch, “Please choose an option” for radios). lkPhone also fails a filled number that is too short or too long (invalidMessage option). lkValidation skips disabled and hidden components and clears their messages.

Rules reference

RuleFails whenDefault message
'required' / { required: true }value is empty: '', null, [], uncheckedLabel is required
'email' / { email: true }not name@domain.tldEnter a valid email address
{ min: n } / { max: n }Number(value) outside the boundLabel must be at least / at most n
{ minLength: n } / { maxLength: n }text length — or the number of picks for multiple dropdown / text pop… at least n characters / Select at least n
{ pattern: /re/ }regular expression does not matchLabel is not valid
(value, component) => true | 'message'the function returns a string (or false → “Invalid value”; a thrown error's message)your string
(value, component) => Promise<true | 'message'>async rule: the promise resolves to a string (a rejection's message counts too)your string

Every object rule accepts message to replace its default text. Object keys can be combined ({ required: true, minLength: 8 }) but share one message, so separate rules usually read better. Except required, rules pass while the field is empty — an optional email field only checks the format once something is typed.

Customizing validation

Custom messages and translations

const t = (key) => i18n[key];   // your translation lookup
Look.lkTextbox('#nik', {
  label: 'NIK',
  rules: [
    { required: true, message: t('nik.required') },
    { pattern: /^\d{16}$/, message: t('nik.format') },
  ],
});

Reusable rule factories

const rules = {
  npwp: (v) => !v || /^\d{15,16}$/.test(v.replace(/\D/g, '')) || 'NPWP must have 15–16 digits',
  notFuture: (v) => !v || new Date(v) <= new Date() || 'Date cannot be in the future',
  oneOf: (list, msg) => (v) => !v || list.includes(v) || msg,
};
Look.lkTextbox('#npwp', { label: 'NPWP', rules: [rules.npwp] });

Cross-field and conditional rules — a rule can read other components

const endDate = Look.lkTextbox('#end', {
  label: 'End date',
  rules: [(v) => !v || !start.value || v >= start.value || 'End must be after start'],
});
const company = Look.lkTextbox('#company', {
  label: 'Company',
  rules: [(v) => type.value !== 'business' || !!v || 'Company is required for business accounts'],
});
type.el.addEventListener('change', () => company.hasError && company.validate()); // re-check dependants

Async rule — e.g. availability check against your API

const isFree = async (v) => {
  if (!v || v.length < 3) return true;                 // let the sync rules report these
  const r = await fetch('/api/users/available?u=' + encodeURIComponent(v));
  const { available } = await r.json();
  return available || 'This username is taken';
};
const username = Look.lkTextbox('#username', { label: 'Username', validate: true, validateDebounce: 500,
  rules: ['required', { minLength: 3 }, isFree] });

await username.validateAsync();   // true / false once the request is back

Changing rules at runtime

password.rules = [...password.rules, { minLength: 12, message: 'Admins need 12+ characters' }];
password.validate();
optionalField.rules = [];          // drop every rule
optionalField.clearValidation();

Styling

An invalid field gets .lk-field--error on its .lk-field wrapper and .lk-input--error on the control; the message is in .lk-field-error. Everything is colored by --lk-negative, so a theme override changes all of them. The message element only exists when the component was created with a label (it builds the wrapper); without one, only the red border is shown.

Server-side validation

Client rules are for fast feedback; the server stays the source of truth. LookUI expects the common HTTP 422 shape — field messages keyed by the field name: { "message": "…", "errors": { "username": ["Username is taken"], "email": ["Domain not allowed"] } } (a value can be a string or an array; the first message is shown). A server message stays until the user edits that field, then the local rules take over again.

1 · Forms: form.submit(handler)

  • Runs validateAsync(); if anything is invalid it stops with { ok: false, reason: 'invalid', errors }.
  • Otherwise it shows lkInnerLoading over the loading element, calls your handler and resolves { ok: true, result }.
  • If the handler throws, field errors are read from the error — { errors } bodies (throw await res.json()), lkDataSource request errors (err.errors), axios err.response.data.errors — and passed to setErrors(). It resolves { ok: false, reason: 'error', message, unmatched, errors }; show message / unmatched as a form-level notice.
  • A second submit while one is running resolves { ok: false, reason: 'busy' } (no double posts).
// Keys that differ from component names: map them
const form = Look.lkValidation(email, phone, { fields: { 'contact.mobile': phone } });

// Without submit(): apply any error object yourself
const unmatched = form.setErrors({ email: ['Already registered'], token: 'Expired' });
// → email shows its message and gets focus; unmatched = [{ key: 'token', message: 'Expired' }]

2 · Grids: lkTable editing

When dataSource.add() / update() rejects with field errors, lkTable shows each message under the matching inline or popup editor, keeps the row in edit mode and puts anything unmatched in the form-level message. An lkDataSource URL transport does this automatically for a JSON error body (the thrown error carries status, body and errors); a function transport can throw { message, errors }. See lkTable — Popup editing (try an existing SKU).

3 · Uniqueness and other remote checks while typing

Use an async rule (above). Keep the server check on submit as well — the async rule is only a preview.
